## 九、测试体系（T-0.11）

分三层，越往下越慢、覆盖越接近真实用户。**每次改动都要跑前两层**，第三层在改界面时跑。

| 层 | 命令 | 规模 | 覆盖 | 耗时 |
| --- | --- | --- | --- | --- |
| 1 · 算法与逻辑单测 | `npm test` | 31 项 | 四柱算法快照、历法换算、弹层状态机、分享参数编解码 | ~0.2s |
| 2 · 界面 e2e（真点界面） | `npm run e2e` | 84 项 | 输入页、高级设置、偏好记忆、地区选择、弹层开合与回填、跳转命盘页、命盘页 6 组交互 | ~45s |
| 3 · 界面截图留档 | `npm run e2e:shots` | 12 张 | 输入页 / 高级设置 / 弹层三态 + 匹配列表 / 填好的输入页 / 命盘专业盘 / 基本盘 / 大运流年 / 无解告警 | ~5min |

e2e 与截图都需要先开自动化通道：

```bash
/Applications/wechatwebdevtools.app/Contents/MacOS/cli auto --project <项目> --auto-port 9530
npm run e2e      -- --ws=ws://127.0.0.1:9530
npm run e2e:shots -- --ws=ws://127.0.0.1:9530
```

### 微信开发者工具的能力边界（2026-09-24，devtools 36.6.0 实测）

这三条决定了「什么能靠点界面验证、什么只能靠单测」，不要重复踩：

| 现象 | 影响 | 我们的做法 |
| --- | --- | --- |
| **自动化树里没有自定义组件内部节点**：`page.$$('.sheet')` 恒为 0、`page.$('ui-icon')` 恒为 0、页面实例的 `selectComponent('datetime-sheet')` 返回 null | 日期弹层里的滚轮、快填框、四柱选项点不到 | 把弹层逻辑整体抽到 `utils/datetimeSheet.js`（纯函数），用单测覆盖；界面层只用截图肉眼验收；页面侧只验证「能打开 / 受控属性灌进去不崩 / 确认结果正确回填」 |
| **一个会话只能扛 3~4 次页面重载**：之后 `page.$` 全返回 null（但 `currentPage()` 仍报 paipan）、命盘页永远 `ready === false`、截图变空白 | 连拍十几张截图必挂 | 截图脚本**每张图重启一次自动化通道**；只重连不重启没用 |
| `mp.reLaunch` 间歇性不生效（隔一条不跳）；刚 `cli auto` 完的两三秒内 `currentPage()` 会抛 `rawPath ... null` | 会存下「看着正常但不是这张表」的假截图 | 跳页后**轮询确认 `currentPage().path`** 再截图；连上后先轮询等页面就绪 |

另外两个小坑：`page.getElementsByXpath` 在这个版本直接抛异常（别试）；往项目目录里写 PNG 可能触发重新编译，所以截图先攒在 `/tmp` 再搬进 `artifacts/`。
